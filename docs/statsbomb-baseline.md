# StatsBomb-based replay baseline migration

## Objective

Long, navigable match timelines now become the primary acceptance baseline for
PitchVolt UI, event state, storytelling and adversarial tests. The original
six-event high-press sample remains as a focused regression test, not our demo
coverage target.

**Two independent provenance classes:**

1. **Real historical StatsBomb Open Data**: explicitly marked historical,
   with source URL, source attribution and SHA-256 of the exact file version.
   Keep real identifiers, coaches, teams, scorelines and substitutions
   faithful to source, never call them fictional or live Premier League.
2. **PitchVolt synthetic**: original fictional teams, identities and results,
   seeded for deterministic reproductions and calibrated against *documented*
   aggregates from a reviewed StatsBomb reference corpus. Never claim any
   external event record was generated by PitchVolt.

`fixture_manifest.FixtureManifest` is the initial enforceable origin boundary,
not a loader. Existing `StatsBombSyntheticSource` explicitly handles **only**
fictional, narrow, StatsBomb-shaped event JSON. It is **not** a historical
Open Data importer and must not be broadened by bypassing its validators.

## Data source and attribution

Official [StatsBomb Open Data](https://github.com/hudl/open-data)
provides competition/season, match, event and lineup JSON; 360 snapshots only
exist for some fixtures. Its README asks that published analysis acknowledge
StatsBomb and display the StatsBomb logo from its Media Pack. Review its LICENSE
before redistribution in a public deployed demo; do not automatically commit
an entire historical corpus or assume a permissive software-style license.

No actual StatsBomb fixture is imported by this PR.

## Compatibility architecture

Source JSON -> source-specific input adapter -> canonical replay records ->
match clock / state / projection -> REST+SSE -> one browser replay cursor.
The core intelligence and UI must not special-case StatsBomb. Provider-specific
event type mapping, period timestamps, normalization of 120x80 to 105x68 metres,
missing optional fields and football terminology belong in the source adapter.

Every input type needs an explicit mapping policy: faithfully mapped,
presentation-only, intentionally ignored (with diagnostic), or rejected.
In particular: Half Start/End, Starting XI, Substitution, Goal, Shot, Carry,
Pass, Pressure, Ball Recovery, fouls, cards and keeper actions; an arbitrary
Ball Recovery is not necessarily a possession turnover, and multi-period
clock semantics must be validated.

The fixture must say whether its score represents a full match or merely a
truncated window; never display 0-0 on an excerpt without explicit initial
score. Show player surname/jersey, crest and substitutions only from a
validated lineup/metadata source.

## Baseline acceptance gates

- At least one hash-pinned real historical fixture for integration tests,
  with explicit provenance and publisher acknowledgement.
- Several seeded synthetic extended scenarios of different tactical types,
  with stable manifest, original player/coach/club identities and event count.
- Temporal invariants: unique ordered IDs, monotonic clocks per period,
  replay pause/seek ±2s, future-event exclusion, metric consistency,
  deterministic score/substitutions and complete match-vs-excerpt policy.
- Playback/performance: frontend usable for thousands of actions without
  keeping a full DOM node for each event; source and derived projections
  deterministic under seeks and speed changes.
- End-to-end tests of lineup and visual identity metadata, synchronized
  stream and commentary, server-controlled text fallback and no Foundry
  inference unless independently authorized.

Related implementation issues: #63 replay clock; #64 historical importer;
#65 longer calibrated synthetic fixtures; #66 unified loader; #58-61 UI.

## Explicit historical file acquisition

Use the [official Open Data repository](https://github.com/hudl/open-data) to select a
numeric match ID and a **full 40-character upstream commit SHA**, and review
attribution/licensing before using its data in any distributed demo.

```shell
uv run --frozen python -m pitchvolt.statsbomb_acquire \\
  --commit <40-character-commit> --match-id <numeric-id> \\
  --output-dir .local-statsbomb/<match-id>
```

This prints the exact download URL without fetching. Append
`--execute-download` to opt in to the download. The command stores the exact
source bytes alongside a JSON manifest containing the SHA-256 and official
commit-pinned source link, then validates the original records with the strict
historical loader. It refuses to overwrite an existing acquisition. Keep these
large external records outside Git until licensing and redistribution review.
A census of original event families is not yet full domain semantic support.

This acquisition path does not download automatically in tests/CI and does not
enable Foundry, Azure billing or historical match display in the public UI.

## Historical presentation projection (partial)

`pitchvolt.providers.statsbomb_projection.project_historical_actions` converts only fully located Pass, Pressure, Carry and Shot into read-only chronological pitch actions, preserving source IDs/names and converting 120 × 80 coordinates into canonical 105 × 68 metres. Every omitted family or record is counted by source event type. Ball Recovery never implicitly becomes a TURNOVER and a Shot never implicitly becomes a canonical GOAL; scoring, substitutions and tactical detection remain unavailable on this incomplete historical projection. This is **not** the application's canonical `MatchEvent` feed and is not yet wired to the public UI. Source-backed period clocks and complete semantic coverage remain tracked in #64.

## Historical action projection edge cases

Source events are all checked for chronological consistency, including types that are not projected. A historical `Shot` without `shot.end_location` remains a displayable shot with an unknown endpoint, not an invented destination; `shot.outcome.name == Goal` is retained as a source-backed annotation but is **not** yet replay score state or a canonical goal. Other event families remain explicitly counted as omitted. Historical extraction and score reconstruction are separate steps, and real corpus acceptance tests are still needed.

## Extended synthetic replay baseline (initial deterministic version)

The `extended_match` scenario contains **220 fictional canonical events across two halves**, including four explicitly fabricated synthetic turnovers and one scripted synthetic goal. Its *broad action-family frequencies only* are weighted to one pinned historical reference (`statsbomb_reference_weighted_actions` evidence marker). The event order, event rates per minute, team tactics, player identities, possession, passing outcomes, goals and scorelines are **not calibrated** and the fixture is not equivalent to a football match simulation. Real Open Data ingestion, distribution estimation, validated lineup/staff metadata and referee/substitution state remain outstanding before issue #65 can be closed. Legacy six-event scenarios remain regression fixtures.

## Source-accurate historical lineups (partial)

The separate `statsbomb_lineups.load_historical_lineups` accepts a locally obtained historical `data/lineups/<match_id>.json` file and an exact SHA-256 checksum, validates two teams, unique players, jersey numbers and available source position names. These are source-backed display records only, not a fabricated starting XI, not a substitution timeline, and not a verified link to the event file until the match-bundle validator is complete. Keep lineups distinct from original fictional PitchVolt player metadata.

## Tactical evidence inside extended synthetic replay

The extended seeded fixture now includes one **explicitly scripted, synthetic** eight-action high-press window (event indexes 71–78), with opponent failed pass under pressure, explicit turnover, carry, attacking pass and successful fictional goal. Those eight events occur inside 20 seconds so the unmodified `MatchProcessor` can publish a source-ID-backed tactical insight. The scripted event families are subtracted from the pinned-reference action quotas before shuffling remaining events; the aggregate action mix remains locked. This arrangement is for deterministic integration coverage, **not** evidence that the tactical sequence occurred in StatsBomb match 9880 or that our fictional goal has a realistic frequency.

## Cross-file historical identity validation

`statsbomb_bundle.validate_historical_bundle` reconciles the independently checksum-verified source event and roster documents. It fails on team IDs absent from the lineup, opposing-team player references, invalid substitution replacement identities and player IDs assigned to both clubs. A player referenced by an event but missing from the lineup is explicitly reported as unknown, never substituted with a guessed name. The report also counts source substitutions and missing player references. This is not yet an authoritative Starting XI, score projection, substitution state machine or full historical UI feed. It does not redistribute historical events or invoke Azure.

## Observational historical goals and substitutions

`statsbomb_state.historical_event_state` materializes explicit goal outcome records and substitution outgoing/incoming IDs, after event/lineup identity validation. This is an **offline historical-source projection**, not a canonical synthetic event stream. Full-match scores are provided only when source event coverage is declared full, both teams occur, and no unresolved scoring classes or missing shot outcome remain; excerpts return `score_by_team=None` even if they contain observed goals. Unresolved own-goal families explicitly disable complete-score claims to avoid double counting. Actual match metadata confirmation, started/substituted rosters, and public API integration are still separate tasks. No billable inference is involved.

## Local unified historical bundle verification

After separately acquiring both events and lineup JSON files for the *same* pinned match/commit, place them under one local directory as `<match-id>.json`, `<match-id>.manifest.json` and `<match-id>.lineups.json`. Keep the original contents byte-identical. Run `uv run --frozen python -m pitchvolt.statsbomb_bundle_report --directory <directory> --match-id <numeric-id> --lineup-sha256 <64-character-digest>`. This requires no network, Azure or LLM inference. The command validates both source hashes and cross-file IDs and emits a conservative JSON report with real-vs-synthetic origin, source attribution, projected action count, omitted families, unknown lineup players, observed goals/substitutions and score availability. It never generates a canonical synthetic MatchEvent stream or enables an unlicensed historical public replay. The first approved historical reference match remains 9880; an official lineup SHA must be acquired separately, not inferred from the event hash.

## Acquire original event and lineup data together

Run `uv run --frozen python -m pitchvolt.statsbomb_bundle_acquire --commit 4b73468fc5b0f1950f9f66fada70ad3a4f9327cb --match-id 9880 --output-dir .local-statsbomb/9880` to review the two commit-pinned URLs without any download. Add `--execute-download` explicitly to fetch both upstream files (each capped at 30 MB), preserve their exact bytes, validate both source formats and cross-file identities, and print the event and lineup SHA-256 values. It refuses existing outputs and rolls back invalid acquisitions. **External downloads are never run by ordinary CI or at app startup.** Keep all original match JSON local pending publisher license/attribution review; existing hosted PitchVolt remains entirely synthetic.

## Complete-time extended scenario and multiple tactical windows

`extended_match` remains a deterministic **fictional** 220-event test sequence and now includes the period-two 90:00 clock endpoint (prior generation sampled a half-open time range and stopped short of regulation). Four deliberately scripted eight-event high-press sequences occur in both halves and yield four tactical insights through the *unchanged* production `MatchProcessor`. At 220 events the pinned source ratio allocates only three shots, so the four-window acceptance fixture deliberately reassigns one Carry quota to Shot. This one-event deviation is documented rather than presented as a calibrated frequency. This is acceptance coverage, not a statistical model of realistic insight frequency or a real full-match simulation; the interstitial event positions and outcomes are still synthetic. The Foundry smoke command now accepts `--scenario extended_match` for offline preflight, defaulting to `high_press` and never invoking inference without both explicit live flags. The source reference and historical JSON remain independent from fictional scenarios.

## Three-class synthetic tactical acceptance coverage

The deterministic 220-event extended match now includes two evidence-backed high-pressure sequences, a sustained-possession sequence and a counterattack, each independently classified by the same streaming `MatchProcessor`. The sustained-possession detector requires a shot/goal, at least six events within 45 seconds of one period, at least four passes, the same possession side throughout, and no intervening turnover. The counterattack is explicitly distinct from the pressured failed-pass high-press sequence. All four evidence windows and the 90-minute endpoint are tested. These deliberately constructed fictional phases are regression acceptance coverage, not a source-derived historical interpretation, realistic event-rate model or licensed historical replay. The broad StatsBomb reference action quotas and the previously documented single synthetic shot-quota adjustment are preserved.
